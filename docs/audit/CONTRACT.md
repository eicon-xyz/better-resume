# 模块设计审计契约（v1）

> 目的：对 better-resume 的每个模块，按用户给的「设计检查清单 + 危险信号速查表」逐条拷问，
> 产出一份**可核对**的问题清单（含原因），最终汇总成单个 HTML 文件地图。
> **规则：每条问题必须能被我按你写的 `file:line` 打开看到证据。写错行号 = 该条作废。**

## 0. 角色

你是设计评审员，不是改代码的人。**不要修改产品代码、不要提交、不要跑测试去"证明"**（可以读测试）。
你只做三件事：读代码 → 判读设计 → 写审计 JSON。

## 1. 唯一交付物

一个 JSON 文件：`docs/audit/units/<你的 unit id>.json`（目录已存在；只写你这一个文件，不要碰别人的）。
写完用 `python3 -c "import json;json.load(open(...))"` 自检能被解析。

## 2. JSON 结构（严格按此，字段名不得改）

```json
{
  "unit": "media",
  "title": "media（转写/TTS 缝 + 句池归并 + 适配器）",
  "scope": ["apps/api/src/better_resume/media/**", "apps/api/tests/media/**"],
  "one_sentence": "一句话：它做什么、给谁用、最重要的 1~3 件事是什么（你的判读，可写出问题）",
  "knowledge": "这个模块独占的那份知识是什么（一个格式/协议/算法/不变量）；别处是否也有同一份",
  "passes": [
    { "dim": "D1 一句话", "note": "为什么这一条没问题（一句话）" }
  ],
  "issues": [
    {
      "id": "media-01",
      "dim": "D3 先写接口注释",
      "signals": ["实现文档污染接口"],
      "severity": "高",
      "title": "TranscriptionChannel 的接口注释里写了讯飞 seg_id 归并细节",
      "where": ["apps/api/src/better_resume/media/transcription.py:42"],
      "evidence": "把原文抄 5~15 行以内进这里（带行号前缀），不要转述",
      "why": "为什么这是问题：引用清单里的判据（如「接口注释里有没有调用者不需要知道的实现细节」），说清调用者被迫知道了什么",
      "fix": "一句话修法（可写「拆出 X」「把参数 Y 改成自动推导」「不要动，因为 Z」）"
    }
  ]
}
```

字段约束：
- `dim` 必须取自下面 §3 的维度编号（如 `D3 先写接口注释` 或 `R9 重复`）。
- `signals` 取自 §4 危险信号表的**信号名原词**（可空数组，但多数条应有）。
- `severity` 三档：`高`（真会咬人：错误的设计决策 / 会扩散的重复 / 调用者被迫了解实现）、`中`（明显可改进，不紧急）、`低`（吹毛求疵/风格）。
- `where` 用**仓库相对路径:行号**。写区间用 `文件:10-24`。至少一条。
- `evidence` 必须是**原文摘录**，不是你的转述。摘录前先 read 那一行确认。
- `fix` 允许写「不该改」并给理由——诚实比凑数重要。
- 同一处代码**只写一条**，不要为凑维度重复报同一件事。
- 每个 unit **6~14 条** issues 为佳；`高` 通常 1~4 条。**宁缺毋滥，但不许注水**：写不出证据的条目删掉。
- `passes` 只写**你实际检查过且确实过关**的维度（每条一句话 + 可选 where）。不要把没查的写进 passes。

## 3. 检查维度（dim 取值）

设计一个模块时：
- `D1 一句话`：能否用一句话写清它做什么、给谁用、最重要的 1~3 件事。写不清 = 设计有问题。
- `D2 设计两次`：有没有证据表明存在（或缺失）2~3 个差异明显的接口方案被比较过；现接口在「上层易用性 > 接口简单 > 通用性 > 实现效率」下是不是最优。
- `D3 先写接口注释`：接口注释是否先于签名的思路存在；**是否含错误模式、前置条件、不变量**。
- `D4 更少通用方法覆盖专用方法`：有没有一组专用方法其实能被一个通用方法覆盖（或反之：通用方法被硬塞进专用语义）。
- `D5 复杂度下沉 or 推给使用者`：复杂度放在了模块里，还是漏给了每个调用者。
- `D6 可自动算出的配置参数`：是否暴露了本可从别处推导的配置/参数。
- `D7 接口注释含实现细节`：调用者不需要知道的实现细节污染了接口注释/文档。

拆分还是合并时：
- `S1 共享同一份知识`：两类是否共享同一份知识（同一格式/协议/算法/不变量）。共享就该合并。
- `S2 拆开后接口更简单还是更复杂`：只有更简单才该拆。
- `S3 重复（知识重复）`：同一份**知识**（不是代码长相）在多处出现。
- `S4 通用/专用是否干净分开`：通用机制里混了某个调用者的专用逻辑；专用代码该上移应用层还是下移驱动层。

写代码时：
- `W1 命名精确+一致`：命名是否精确、跨模块一致；有没有 `data`/`time`/`count` 式模糊名。
- `W2 消除特殊情况`：是否用定义消除了 if 空值/边界判断，还是到处加 if。
- `W3 错误靠定义规避`：错误是类型/定义层面排除的，还是每个调用者都要处理。
- `W4 注释只写难理解的内容`：注释讲意图/为什么/概念框架，还是复述代码；是否过期。
- `W5 多返回值用具名字段类`：多返回值是否用具名字段的类/结构，而不是 tuple/Pair/dict。
- `W6 符合周围约定`：是否与仓库既有约定一致（AGENTS.md / CODING_STANDARDS.md / 同层其它模块）。

改代码/提交时：
- `C1 改动让设计变好一点`：从 git 历史/代码形态看，近期改动是否在改善设计（找证据，如注释掉的旧实现、兼容层）。
- `C2 注释在代码附近且同步`：注释是否贴着它描述的代码、是否与代码同步。
- `C3 性能改动测量过`：性能相关的代码/常量/缓存有没有测量依据（注释、docs/perf、票据）。

评审时：
- `R1 删除测试`：删掉这个类/方法/模块，调用方是变简单还是变复杂。变简单 = 透传/浅模块。
- `R2 重要的 1~3 件事`：它最重要的 1~3 件事，有没有出现在接口、命名和高频路径上。

危险信号（每条对应一个信号，用 `R<编号>` 作为 dim）：
- `R3 浅模块`、`R4 信息泄露`、`R5 时间分解`、`R6 过度暴露`、`R7 多类症`、`R8 透传方法`、`R9 透传变量`、
  `R10 连体方法`、`R11 重复`、`R12 通用专用混合体`、`R13 注释重复了代码`、`R14 实现文档污染接口`、
  `R15 模糊的名称`、`R16 难以选取名称`、`R17 难以描述`、`R18 难以理解的代码`

## 4. 危险信号判据（原表，别改词）

| 信号 | 一句话判据 |
| --- | --- |
| 浅模块 | 接口并不比实现简单多少；文档比代码还长 |
| 信息泄露 | 同一个设计决策出现在多个模块里 |
| 时间分解 | 代码结构跟着执行顺序走，而不是跟着知识走 |
| 过度暴露 | 用常见功能还得先了解罕见功能 |
| 多类症 | 「类是好的，所以类越多越好」，结果一堆小类各自带一个接口 |
| 透传方法 | 除了转调同签名方法什么都不做 |
| 透传变量 | 变量只是路过一串不使用它的方法 |
| 连体方法 | 不理解 A 的实现就无法理解 B 的实现 |
| 重复 | 同一份**知识**反复出现（不是代码长得像） |
| 通用专用混合体 | 通用机制和某个调用者的专用逻辑混在一个类里 |
| 注释重复了代码 | 删掉它，读者不损失任何信息 |
| 实现文档污染接口 | 接口注释里写了调用者不需要知道的实现细节 |
| 模糊的名称 | 名字宽泛到无法传递有用信息（`data`/`time`/`count`） |
| 难以选取名称 | 起不出精确又直观的名字 → 设计有问题 |
| 难以描述 | 要完整描述一个变量/方法，文档必须写很长 → 分解有问题 |
| 难以理解的代码 | 快速阅读无法理解其含义与行为 |

## 5. 跨模块观察（重要）

如果发现「同一个设计决策出现在多个模块」（信息泄露 / 重复知识），**照常写进你的 issues**，
但把 `where` 写成**两处**（你的模块 + 你看到的那一处），并在 `why` 里点名对方模块。
我会把所有 unit 的 `R4 信息泄露` / `R11 重复` / `S3 重复` 归并成跨模块一览。

## 6. 写法红线

1. **不许凭印象**：每条 evidence 都来自你 read/grep 到的真实行；写之前确认行号。
2. **不许"改进建议清单"**：这是审计，不是需求池。没有判据支撑的偏好不写。
3. **不许复述**：`why` 必须回答"调用者/维护者为此付出了什么代价"。
4. **不许注水**：查过且没问题的放 `passes`；只在 `passes` 里放你**实际读过**的维度。
5. **中文**：全文简体中文；专有名词/代码标识符保留英文。

## 7. 示例条目（照这个粒度写）

```json
{
  "id": "EXAMPLE-01",
  "dim": "R12 通用专用混合体",
  "signals": ["通用专用混合体"],
  "severity": "高",
  "title": "句池归并（通用机制）里硬编码了讯飞 seg_id 的专用语义",
  "where": ["apps/api/src/better_resume/media/assembler.py:88-104"],
  "evidence": "88:  if seg_id in self._seen_sentence_ids:\n89:      # 讯飞会把同一句分多次推，seg_id 相同的必须丢弃\n90:      continue",
  "why": "句池归并是「把增量包按句子聚成可提交文本」的通用机制，但 88-90 行把「讯飞 seg_id 同值即重复」这一条某个供应商的专用知识写死在通用循环里；换一个不带 seg_id 语义的适配器（如 qwen 批量）时，这条规则要么误伤要么成为死代码，维护者必须理解讯飞协议才能改这段通用代码。",
  "fix": "把「这个包是否与已提交句子重复」提升为适配器提供的判定（或把 seg_id 归一化在 adapter 内完成），assembler 只依赖一个 unify 后的句子键。"
}
```

（示例里的行号与内容是**编的**，仅示范粒度；你必须给出真实证据。）
