## Q1 账号范围

M1 的 dev 会话端点（`POST /api/v1/auth/session`）已能让前端拿到 cookie session。
提议 M2 继续用它，真实注册/登录/密码哈希仍推后（本里程碑的验收是「简历 → 面试 → 报告」，
不是「账号体系」）。若你希望 M2 就做真实登录，我加一张票（+1 会话）。

## Q2 简历文件存储

提议：`data/resumes/{user_id}/{sha256}.pdf`（compose 加一个卷），DB 只存
`resume_path/resume_sha256/resume_size`。好处：同一份简历重复上传自动去重；
坏处：单机卷（M6 若要对象存储再换）。**需要你确认是否需要「简历删除」接口**（我默认不做）。

## Q3 雷达图维度

旧项目四维来自神态+评分的混合（神态已砍）。提议四维 = **准确性 / 深度 / 表达 / 结构性**，
由每题 `focus_points` 命中率 + `score` 聚合推导（纯函数、可测试），LLM 只写文字建议。
若你有更想要的维度名（例如「技术深度/沟通表达/逻辑结构/岗位匹配」），直接替换。

## Q4 阈值与上限

`max_follow_up=2`、`low_score_threshold=60`（旧项目 LiteFlow 里的数字）。
这两个值会进决策函数的参数注入，改起来只动一处。

## Q5–Q7 状态与并发的落点

M2 是单体单机：两层状态（会话 + 流程）都放 Postgres、幂等靠唯一约束、题级锁用进程内锁。
旧项目的 Redis Hash + Lua CAS + Redlock 是分布式形态，M6 再迁移（D07 的「不养死代码」）。

## Q8 报告总结句

提议：`summary` 由 LLM 写 2–3 句（走 llm-gateway，失败/无 key 时留空并在 UI 标注「未生成总结」），
分数与维度**绝不**让 LLM 决定。

## Q9 题量

默认 5 题、上限 10 题；前端可调（3/5/8）。真实演示用 5 题（约 6–10 次 LLM 调用）。

## Q10 前端图表

自绘 SVG（对齐旧项目「手绘 SVG 雷达」的做法），不引 recharts/d3——依赖少、截图稳定。
