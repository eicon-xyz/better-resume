## 4. 与原方案的取舍（对齐 D 决议 + 补 M1 的经验）

1. **状态机不用 Redis Hash**：M2 把两层状态都放 Postgres（`interview_sessions.status` +
   `interview_flow_state` 行 + `version` 乐观锁）。旧项目用 Redis Hash + Lua CAS 是为了扛并发；
   我们是单体单机（M6 才上分布式），Postgres 事务 + version CAS 已经把不变量守住，且可测。
2. **幂等靠数据库唯一约束**：`interview_answers.request_id` 唯一 + 幂等表记录响应，重投直接回放，
   不引 Redis processing/replay 双 key。
3. **题级锁进程内 + DB 兜底**：M2 用 `asyncio.Lock` per (session, question) + 唯一约束；
   Redis 分布式锁留 M6（D07 的「诚实原则」：不写过期就死的 Lua）。
4. **追问裁决是纯函数**：四道判定（完成短路 / 超限 / AI 建议 / 低分 / 要点缺失）+ fail-open，
   穷举转移表测试（对齐 §4.1.3，但不引 LiteFlow）。
5. **报告不交给 LLM 编**：分数/维度/逐题数据都是聚合出来的确定值；LLM 只允许写一段总结句，
   且失败不影响报告可用（延续 D10 的反幻觉分工）。
