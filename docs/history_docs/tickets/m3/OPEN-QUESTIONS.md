## Q1 聊天流的单飞

run() 的返回值可能是流。三个选项：

- **A（提议）**：在飞合并 + 广播。两个并发同 key 请求只打开一条上游流，
  后到者从头回放同一批帧，内容逐字节一致；流结束后同 key 再请求 → **新开**上游流。
- B：聊天链路根本不进单飞（只有评分/追问/出题/报告去重）。改动最小，但
  "并发同 key 单次调用"的验收就少了一条最有说服力的链路，也与 §12.2 的
  "chat 链路只 import 这一个方法"不一致。
- C：连完成后的流也做 TTL 回放（旧项目 600s 结果回放）。最省 token，
  但用户**故意**连问两次同一句话会拿到第一次的答案——语义错误，我反对。

## Q2 回放 TTL

回放 = 同一 key 的第二次调用直接返回上次结果、不触碰上游。

- **A（提议）**：分阶段。评分/追问 60s（重答同一题同文本会复用分数）、出题 300s
  （同一份简历反复进出题）、报告总结 60s；**chat 0**；失败只负缓存
  "schema 校验失败"这类不可重试错误 10s，超时/过载/供应商抖动**不缓存**——
  这样 M2 的「评分失败 → 回滚 → 可重答」不变量不受影响。
- B：完全不回放，只做在飞合并。零语义风险，但省不下"用户重试/刷新导致的重复调用"。
- C：照抄旧项目 600s 成功 / 60s 失败。简单，但那两个数字是为旧项目的
  "分布式 + 长面试"调的，我们没有对应证据，写进代码只是抄数字。

## Q3 限流的作用点

- **A（提议）**：Starlette 中间件，按路由类别分桶。run() 签名保持 §12.2 原样，
  四个调用点不动；身份用会话 cookie 的 sha256（不查 Redis、不落原文），无 cookie 用 IP；
  429 + Retry-After。
- B：只在 run() 内部限 ai-call 一种桶。省掉中间件，但"读接口被刷"这类问题不管，
  且 run() 拿不到用户身份（要么改签名、要么按 key 前缀猜）。
- C：A + run() 内部再计一次。覆盖最全，但同一请求会被两层重复计数，
  参数会变得难以解释——除非你要"按 stage 的 AI 调用预算"，那是配额不是限流，建议 M3 不做。
