# 子智能体操作约定（better-resume）

> 来源：2026-10 那次「模块设计审计 → 修 ai-02 → 双轴评审 → retro」的实践。
> 只写「怎么做 + 为什么」；技能本身怎么用、怎么写 prompt，不在这里复述。

## 1. 先建任务，再派活

- 先 `team_task_create` 写清三件事：**范围**（读哪些文件）、**唯一写入路径**、**验收口径**（怎么算完成）。
- **一个任务一个写入路径**——两个成员写同一个文件必然互相覆盖，且失败后分不清是谁写的。
- prompt 要自包含：子代理看不到你的上下文，把「参考样例」与「红线」一起贴进去。

## 2. 写范围不重叠

- 并行成员各写各的文件/目录；**同一份文档不要两人同时写**（要改就串行，或指定唯一作者）。
- 需要共享事实时，先落成文件（例：`var/review-brief.md`、`var/review-spec.md`）再让成员读，不要靠消息复述。

## 3. 结构化产出先给契约

- 要结构化产出（例：审计单元）时，**先给 JSON 契约 + 一个手写样例**，再并行；否则每人一套字段名，汇总全是胶水代码。
- 每条断言必须带 **`文件:行号` + 原文摘录**：没有行号的结论无法复核，等于没写；行号写错就是废条目。
- 交付前让产出方自己先跑一遍校验脚本（下条）。

## 4. 证据核对用脚本，不信自述

- 「我做完了」不算证据。用脚本核对，本项目现成的三件：`scripts/verify_audit_evidence.py --strict`（引证逐字核对）、
  `scripts/verify_mutation.sh`（测试是否真钉住实现）、`bash scripts/verify.sh --layer scripts`（脚本语法 + 结构校验）。
- **核对脚本自己也要被验证**：先让它对已知的坏输入红一次。否则你只是又造了一个「恒绿的检查」。

## 5. 评审：双轴并行，不合并结论

- `/code-review` 的 Standards 与 Spec **分开跑**（不同子代理、不同上下文），回报时**并列不重排**——
  「一轴通过、另一轴失败」是常态，合并排名会把它掩盖掉。

## 6. 席位、失败与 fork

- 团队席位上限 **8**（含 lead）。
- **provisioning 失败的成员仍占名额，且名字被永久占用**：失败后不要同名重试（会报 name taken），
  换个名字或用 `subagent_fork`——**fork 不计入席位**，这是席位满时唯一还能并行的路。
- 需要独立上下文（不想被主上下文影响）用 `subagent_fork`；需要长期并行改多份文件才用 team 成员。

## 7. 等待与超时

- `wait_agent` 只在**有其它成员正在运行**时才有意义；全员 inactive 时它会立刻返回，不要空等。
- `run_code` 的 `timeoutMs` 上限与默认值见 `AGENTS.md` §AI 智能体须知（**只在那里写数值**）：想等更久就分多次调用，不要指望一次 `wait` 等十分钟。
- 长任务用后台 job（`run_in_background`）启动，期间去做别的事，不要忙等。

## 8. 跨模型交接与评审分派

### 8.1 何时用

执行方与规划方不是同一个模型、也不是同一个会话时——含子智能体、`subagent_fork`、以及把票据交给另一款模型执行。

### 8.2 交接包五栏（缺一不可）

| 栏 | 要求 |
| --- | --- |
| 范围 | 要读哪些文件（给路径）；读不到就别猜，停下来问 |
| 唯一写入路径 | 只许写这一个文件或目录；两个执行方写同一路径必然互相覆盖（见 §1） |
| 验收口径 | 可复跑命令 + 预期读数（数字或字符串）；不许写「跑通即可」「无报错」；命令还要**数得对**（见 §8.8） |
| 红线 | 不许碰的对象（文件、节、依赖、既有格式） |
| 不接受的自由度 | **明确列出**执行方不许自行发挥的判断点（见 §8.3） |

### 8.3「不接受的自由度」

定义：spec 没写、但执行方**不许自己补**的地方。它与「红线」的区别是——红线是不许碰的**对象**，不接受的自由度是不许做的**判断**。

例子：

- 不许重排或重编号既有章节；
- 不许顺手重构与本次无关的代码或文档；
- 不许新增依赖；
- 不许把实现偏差写成新的业务规则（`AGENTS.md` 硬规则 3）；
- 不许扩大写入路径；
- 不许修改 spec 或票据的既有内容（只允许在末尾追加自己那两段自述）。

### 8.4 冲突处理

spec 与现实冲突、或需要的信息不在交接包里 → **停下来报**，不许自行补规格。对应 `AGENTS.md` 硬规则 3：未经用户确认的实现偏差，不得写成新的业务规则。

### 8.5 评审双轴分派

| 轴 | 谁跑 | 唯一任务 |
| --- | --- | --- |
| Spec 轴 | **异家族同级**模型（例：执行方是 `opencode-go/deepseek-v4.1-flash` → 评审方用 `dashscope/qwen3.8-flash`） | 比对「票据里的意图复述 / spec 与票据要求 / 实际 diff」三者，找出**不一致** |
| Standards 轴 + 意图一致性 | 规划方（掌握意图与仓库规范的那一方）；**规划方与执行方同家族时改派异家族**（见下） | 对照 `CODING_STANDARDS.md` 与票据红线，找违规与越界 |

- 评审方与执行方**不同款（不同家族）**。子代理可用路由全是 flash 级、没有更强的档，所以这一栏的价值来自**盲区不共享**，不是「用更强的模型审」。
- **规划方与执行方同家族时，Standards 轴也必须外派。** 同家族 = 盲区共享，此时规划方审自己派出去的活等于自审；
  而规划方看不见自己写下的洞，这类缺陷通常要等异家族评审或执行方主动交代才浮现。
  规划方保留的只有**家族无关的机械核对**：重跑每条验收命令、核 `git diff --numstat`、比 sha256 基线（§8.7）、
  查写入路径有没有越界、确认冻结文件零改动。这些不需要判断力，但**一步都不能省**。
- 评审的产出是**两轴并列的发现清单**，不合并、不重排（见 §5）。
- 评审的任务是**找不一致**，不是评价设计好坏；任务越窄，弱模型越可靠。

### 8.6 为什么单列「不接受的自由度」

指望模型自己判断边界，不如把不许发挥的地方显式写出来——执行模型越弱，这一栏越值钱。

### 8.7 派活前给票据建基线

`docs/tickets/<stage>/` 在提交前是 untracked，`git diff` 对票据没有输出——评审方因此无法核验「票据正文有没有被执行方改过」，只能报「无法判定」。

做法：派活前把票据与各票目标文件的 sha256 落成快照，每轮之后用 `sha256sum -c` 核验越界。

```bash
mkdir -p var/<stage>-baseline
sha256sum docs/tickets/<stage>/*.md <各票的目标文件> > var/<stage>-baseline/pre-dispatch.sha256
sha256sum -c var/<stage>-baseline/pre-dispatch.sha256   # 收口时核：只有预期文件应 FAILED
```

`var/` 已 gitignored，快照不进仓库——所以**核验读数要抄进验收包**：只引一个不入库的路径等于没有证据。

**每一轮派活前都要重新快照。** 上一轮的快照在本轮开工时已经过期（上一轮就改过那些文件），拿过期快照去核验会得到对不上的读数，执行方只能退回 `git HEAD` 当基线、并自己声明这一点。

### 8.8 验收命令要先证明它数的是你想数的东西

断言文档结构时，命令数的往往不是你以为的东西。例：要断言「`CODING_STANDARDS.md` §6 有 8 条必答问题」，用
`awk '/^## 6/,0' CODING_STANDARDS.md | grep -c '^- \*\*'`（数问题标题行），不要用 `grep -c '^- '`
（数的是所有顶格 bullet：导语里的列表项会被一起数进去，缩进子列表又数不到）。

命令数错的后果不是「检查失败」，而是**执行方绕着它写、并为绕法编一个听起来合理的理由**——产物可能仍然合规，
但交代的「为什么」是假的，而那一栏的全部价值在于它可信。这与 D22「只打印结论、不判定的验证脚本视为缺陷」是同族问题：**断言本身也要被验证**。
