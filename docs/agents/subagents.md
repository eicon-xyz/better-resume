# 子智能体操作约定（better-resume）

> 来源：2026-10 那次「模块设计审计 → 修 ai-02 → 双轴评审 → retro」的实践。
> 只写「怎么做 + 为什么」；技能本身怎么用、怎么写 prompt，不在这里复述。

## 1. 先建任务，再派活

- 先 `team_task_create` 写清三件事：**范围**（读哪些文件）、**唯一写入路径**、**验收口径**（怎么算完成）。
- **一个任务一个写入路径**——两个成员写同一个文件必然互相覆盖，且失败后分不清是谁写的。
- prompt 要自包含：子代理看不到你的上下文，把「参考样例」与「红线」一起贴进去。

## 2. 写范围不重叠

- 并行成员各写各的文件/目录；**同一份文档不要两人同时写**（要改就串行，或指定唯一作者）。
- 需要共享事实时，先落成文件（例：`var/review-brief.md`、`var/review-spec.md`）再让成员读，不要靠消息复述。

## 3. 结构化产出先给契约

- 要结构化产出（例：审计单元）时，**先给 JSON 契约 + 一个手写样例**，再并行；否则每人一套字段名，汇总全是胶水代码。
- 每条断言必须带 **`文件:行号` + 原文摘录**：没有行号的结论无法复核，等于没写；行号写错就是废条目。
- 交付前让产出方自己先跑一遍校验脚本（下条）。

## 4. 证据核对用脚本，不信自述

- 「我做完了」不算证据。用脚本核对，本项目现成的三件：`scripts/verify_audit_evidence.py --strict`（引证逐字核对）、
  `scripts/verify_mutation.sh`（测试是否真钉住实现）、`bash scripts/verify.sh --layer scripts`（脚本语法 + 结构校验）。
- **核对脚本自己也要被验证**：先让它对已知的坏输入红一次。否则你只是又造了一个「恒绿的检查」。

## 5. 评审：双轴并行，不合并结论

- `/code-review` 的 Standards 与 Spec **分开跑**（不同子代理、不同上下文），回报时**并列不重排**——
  「一轴通过、另一轴失败」是常态，合并排名会把它掩盖掉。

## 6. 席位、失败与 fork

- 团队席位上限 **8**（含 lead）。
- **provisioning 失败的成员仍占名额，且名字被永久占用**：失败后不要同名重试（会报 name taken），
  换个名字或用 `subagent_fork`——**fork 不计入席位**，这是席位满时唯一还能并行的路。
- 需要独立上下文（不想被主上下文影响）用 `subagent_fork`；需要长期并行改多份文件才用 team 成员。

## 7. 等待与超时

- `wait_agent` 只在**有其它成员正在运行**时才有意义；全员 inactive 时它会立刻返回，不要空等。
- `run_code` 的 `timeoutMs` 上限是 **120000**：想等更久就分多次调用，不要指望一次 `wait` 等十分钟。
- 长任务用后台 job（`run_in_background`）启动，期间去做别的事，不要忙等。
