## 1. 为什么单独一个阶段

M6 的所有 AI 调用都打在确定性假供应商上（`scripts/fake_openai.py` + `smoke-fake` 模型行）。
这让我们能证明"我们自己的代码是对的"，但**证明不了**：真模型的延迟/限流/错误语义、讯飞 AST 真机链路、
星云工作流真机字段、真实浏览器麦克风、Redis 故障与长跑稳定性。这些是**验证欠账**，不是功能缺口。

## 2. 阶段目标（可验收的成功标准）

1. `docs/perf/M6-capacity.md` §2.4 不再是"留空"，而是有**真模型数字**（单独成节，不与假上游混表）；
2. 四条 AI 链路（对话/出题/评分+追问/报告总结）在**真模型**下各留下一次可复跑的端到端证据；
3. 讯飞 AST 与星云工作流：真机跑通或**明确记录失败原因**（凭据缺失/字段不符），不允许"跳过但不说"；
4. 真实浏览器的人工 4 步清单由你执行并回填结果（我做不了麦克风点击，只能提供清单与自查页）；
5. 不需要凭据的那部分（浸泡 + Redis/worker 故障注入）在本机做完，给出数字与结论；
6. 全部结论汇总到 `docs/tickets/v1-verification/ACCEPTANCE.md`（含未验证项与偏差）。

## 5. 验收口径（写清楚什么算"验过了"）

- **真模型证据**必须包含：响应的 `model` 字段、真实 token 用量（`usage`）、端到端耗时分布、以及
  `docker compose logs api` 里对应的 `ai_call_started/finished` 结构化日志；**不得**用假上游的数字冒充。
- **真机证据**（讯飞/星云）必须包含：真实请求/响应的脱敏片段（`cn.st` 帧、星云 SSE 帧）、字段映射表、
  以及错误码路径的实际表现；失败也要留原始报错。
- 每条票据的交付物 = 一个可复跑脚本（或已有脚本的新参数）+ 验收文档一节 + 必要的 `PROBLEMS.md` 条目。
- 本阶段**不改业务代码**，除非真机证明某处映射/契约是错的——那也要先红-绿补测试，并在台账里写清。

## 6. 不做

- 不做 Kubernetes / 多可用区 / 服务网格（M6 已定不做，本阶段也不补）；
- 不做真实付费压测（不把供应商额度当压测目标）；
- 不引入新供应商（只验已有的三家：DeepSeek / 讯飞 / 星云）；
- 不为了"看起来绿"而放宽断言（真机失败就写失败）。
