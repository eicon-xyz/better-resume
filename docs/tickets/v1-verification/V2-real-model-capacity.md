# V2 — 真模型容量：填充 §2.4 + 找我们自己的拐点

- blocking：V1（脚本与凭据先跑通）
- 纪律：数字只来自 `--json` 产物；与假上游的数字**分表**呈现

## 目标

1. 把 `docs/perf/M6-capacity.md` §2.4 从"留空"变成"有真模型数字"（小并发，标注模型 id 与时间）；
2. 找出**我们自己的**拐点：固定假上游（无限快）逐级加压，观察 p99 抬升与 `http_5xx` 出现的并发点，
   判断瓶颈在 uvicorn worker 数、Postgres 连接池还是 Redis；
3. 与 §2.1–2.3（假上游）对照，得出"真供应商延迟把 p95/p99 推高多少"的结论，**不外推**。

## 交付物

- `apps/api/scripts/load_test.py` 增加 `--tag real|fake`（写进 JSON，避免混表）+ `--stage-mix`（可选）
- 真模型三组数字：`chat-sse c=2 d=10`、`answer-submit c=2 d=10`（真模型评分）、`mixed c=4 d=20`
- 假上游分级加压：`c=10/20/40/80` 各 20s（同一栈），记录 p50/p95/p99、RPS、5xx、429
- `docs/perf/M6-capacity.md` 新增 §2.4（真模型）与 §2.5（我们自己的拐点），并在 §3 瓶颈分析里给结论
- `docs/perf/README.md` 补"真模型怎么跑（含花费提醒与 `--tag`）"

## 测试与验收

| 用例 | 断言 |
| --- | --- |
| `--tag` 生效 | JSON 里 `tag` 字段存在且影响文件名/表格标题 |
| 真模型数字 | 每轮 `count>0`、`error_rate` 有解释、`sse_first_frame_ms.p50` 与假上游对照写明 |
| 拐点实验 | 至少 4 个并发档位；拐点结论必须引用具体数字（哪个档位 p99 翻倍、5xx 首次出现） |
| 诚实性 | §2.4 与 §2.1–2.3 分表；不确定项章节新增"真模型方差"一条 |

## 不做

- 不做供应商侧压测（不给 DeepSeek 打高并发）；不做 >10 分钟长跑（那是 V6）；不调参优化（先量后调）。
