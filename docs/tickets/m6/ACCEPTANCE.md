## 1. §12.4 硬验收：kill 实例端到端（T8）

命令：`bash scripts/kill_instance_drill.sh`（起栈 → nginx + 2×api + worker + fake-llm → 走完半程面试 →
`docker kill` 正在服务该会话的实例 → 经 nginx 由另一个实例接管 → 继续答题/restore/finish/report）

断言逐条对应：

| 验收要求 | 实测 | 证据行 |
| --- | --- | --- |
| 请求落到**另一个**实例 | `served=6f39c80a0fc1` → `survivor=f9ba0be79fc3`（`X-Instance-Id`） | `nginx now routes to …` |
| kill → 恢复耗时 | **237 ms**（另一次运行 5448 ms：nginx 需先失败掉死上游再摘除，见 §7 偏差） | `kill -> recovery` |
| 题号 / 已答数 / 分数 / 追问计数不丢 | kill 前后 `state` 字典**逐字段相等**（题号 1-F1、answered 1、score 55.0） | `state before/after kill` |
| 重试不重复计费 | 同 `request_id` 重放 → `replayed=True`，分数不变 | `replayed request on …` |
| 报告数字 = 冻结值 | overall 55.0、四维、9 个 turn 的分数全部来自 kill 前的作答 | `frozen report` |
| 排队任务在别的进程完成 | `summary_pending=True` → worker 写出总结 | `report summary from the worker` |
| 分布式组件真的在 Redis 里 | 半程 `hot_state=1`，结束时锁已释放、热层被写路径失效（0） | `redis keys mid-flow` / `at the end` + key sample |

> `locks=0`/`singleflight=0` 是**正常**值：锁在答题结束即释放，单飞结果只在调用进行中与回放窗口内存在。
> drill 同时打印它统计的原始 key 样本，便于核对（见 PROBLEMS P14）。

## 2. 分布式单飞 / 锁的机制证据（T1/T2/T3）

| 机制 | 断言 | 位置 |
| --- | --- | --- |
| 题级锁互斥 | 两个并发请求只有一个拿到锁；另一个等待后接管 | `tests/test_distributed_lock.py`（10 例，含续租/过期/释放者校验） |
| 跨实例单飞 | 两个 `RedisFlight` 实例并发同 key → 上游只被调用 **1** 次；结果按 replay TTL 回放；失败可缓存 | `tests/test_distributed_flight.py`（10 例） |
| fencing | 租约过期的 owner 回来写结果会被拒（fencing token） | 同上 `test_stale_owner_is_fenced_out` |
| 热层 + 失效 | 读命中热层报 `source="hot"`；写路径失效后回到 `derived` | `tests/test_hot_state.py`（8 例）+ 6 个回归用例 |
| 任务队列 | 去重、重试、死信、XPENDING+XCLAIM 崩溃接管 | `tests/test_job_queue.py`（7 例） |
| worker 韧性 | Redis 抖动后循环继续；干净停止删心跳 | `tests/test_worker_loop.py`（4 例） |
| 两实例只调一次上游（HTTP 层） | 场景绑定 + 单飞：`tests/test_distributed_flight.py::test_two_instances_call_the_vendor_once` | 同上 |

## 6. 未验证项（诚实清单）

1. **真模型**：本轮所有 AI 调用都打在确定性假供应商上（成本/稳定性考虑）；真实 DeepSeek/星云的高并发、
   限流与长尾延迟**未测**（容量报告 §2.4 为空）。
2. **真机凭据相关**：M4 讯飞 AST 真机、M5 星云真机仍未验证（本机无凭据）——与 M4/M5 的 ACCEPTANCE 一致。
3. **真实浏览器手测**：M6 未改动前端，但"麦克风采集/播放"的人工 4 步清单仍未在真浏览器执行过。
4. **多可用区 / Redis 集群 / 网络分区**：只有单机 Redis；"分布式"覆盖的是单机多进程。
5. **生产网络与 LB**：nginx 在 compose 内网，没有真实 LB 健康检查抖动与跨机 RTT。
6. **长时间稳定性**：压测窗口 15–20s，未做 >10 分钟浸泡（内存/连接泄漏）。
7. **默认分布式开关**：`BR_FLIGHT_BACKEND`/`BR_LOCK_BACKEND`/`BR_HOT_STATE_BACKEND` 的默认值仍是
   `memory`（单进程开发友好）；compose 里全部显式设为 `redis`，drill 就是在 `redis` 下跑的。

## 7. 与提案的偏差清单

| 偏差 | 原因 | 影响 |
| --- | --- | --- |
| `extract_api_index.py` 落在 `apps/api/scripts/`（票据写 `scripts/`） | 与 `export_openapi.py` 同层、共用 api 的 uv 环境（脚本要读 `apps/api/openapi.json`） | 仅路径；CI 与文档已同步 |
| T5 的 `apps/web/Dockerfile` 只做静态站点，反向代理由同一个容器的 nginx（挂载 `deploy/nginx.conf`）承担 | 一个入口容器同时提供 SPA 与 `/api` 反代，避免再拆一个 nginx 服务 | 与票据的"nginx 服务"等价，服务名仍叫 `nginx` |
| 新增 `migrate` 一次性服务与共享 `uploads` 卷 | 起栈时没有迁移会 500（P10）；简历文件必须每个副本可见（P11） | 服务数 6（含 migrate，退出即完成）；票据未禁止 |
| 压测 `answer-submit` 场景实测被默认限流削峰（429 >96%） | 脚本无思考时间 + 默认 20 req/s 桶 | 该场景数字标注为"限流下的表现"，不是答题容量（容量报告 §2.3） |

| 真实 kill→恢复耗时两次分别 237 ms / 5448 ms | nginx 何时发现死上游取决于请求时序（`fail_timeout`） | 两个数字都写进 §1，不取最好看的那个 |
