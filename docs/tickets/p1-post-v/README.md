## 2. 票据拆分（按价值排序，可裁剪）

### P1-A｜Paraformer 实时 ASR：边说边出字（主票，默认必做）

> **状态：已完成，待用户验收**（2026-09-15）。证据：`P1-A-EVIDENCE.md`；
> 首个增量 0.56s、松手→final ≈1.1s（修复 P24 前 10.1s）、关闭码 1000；全量后端 692 / 前端 161 全绿。
> `.env` 已切 `paraformer-rt` 并重建栈；剩真实浏览器手测（用户）。

- **现状**：`TranscriptionChannel` 协议（start/send_audio/stop/wait）本就支持增量——
  事件是 `replace|archive|final`（见 `media/models.py`、`media/protocols.py`）；前端
  transcriptStore 已按增量语义渲染（P23 后追加+去重，绝不覆盖手写）；`xunfei_ast.py` 是
  流式参考实现（句池归并 pgs/rg/seg_id）；但当前默认 `qwen_asr.py` 是**批量**（整段音频
  → 一个 final），句池归并不被触发。
- **做什么**：新增 `media/adapters/paraformer_rt.py`（百炼实时语音识别 WS 协议：
  16k PCM 帧 → 增量 `replace` 事件 + 松手 `final`）；配置
  `BR_MEDIA__TRANSCRIPTION_ADAPTER` 支持 `paraformer-rt`；**真机验证通过后把默认转写
  切到实时方案**（前端提示文案同步从"松手后出字"改回"边说边出字"）——不留"默认关闭、
  没人跑"的分支。
- **交付物**：新 adapter + 配置 + `media_smoke.py --paraformer-rt-real` +
  `v3_ws_probe.py` 实时模式（端到端：nginx → 票据 → 增量帧 → final → 关闭码 1000）+
  前端文案/用例同步 + `P1-A-EVIDENCE.md`。
- **测试与验收**：本地假 WS 服务端（M4 对讯飞的做法）覆盖帧组装/增量事件/断线重连/超时/
  空音频；真机验收口径：边说边出字（增量帧间隔与首字延迟有数字）、松手出 final、
  archive 事件出现（句池归并被激活的证据）、关闭码 1000。
- **预估**：1–1.5 会话（V3 当时的预估）+ 真机排障缓冲；真机调用 ~30–60 次。
- **预检结果（2026-09-15，已实测 ✅）**：用现成 `BR_DASHSCOPE_API_KEY` + `data/audio/v3-sample-16k.wav`
  直连 `wss://{WorkspaceId}.cn-beijing.maas.aliyuncs.com/api-ws/v1/inference`（与批量 ASR 同一业务空间域名，
  **API 不变、零新凭据**；官方文档见「Paraformer 实时语音识别 WebSocket API」，鉴权在握手 `Authorization: Bearer`）：
  `paraformer-realtime-v2` 一次跑通——0.05s `task-started`；PCM 流入后收到 **10 个增量 partial**
  （`你` → `你好` → `你好，我是` → … 逐字增长）；1.80s 收到 final 全句 + 干净 `task-finished`。
  增量事件与 `replace/archive` 语义天然对齐，句池归并（亮点③）可被真实触发。
  注：预检以 3× 实时速率灌文件，partials 同帧到达；真实浏览器按实时节奏推流时增量边说边到，
  端到端 + 人工手测在 P1-A 内补证。
- **风险**（预检后大幅收窄）：浏览器实时推流节奏下的增量到达分布待端到端验证；
  备选 `qwen3-asr-flash-realtime`（Qwen-ASR-Realtime，OpenAI-realtime 风格会话协议，未验证）——
  若 Paraformer 在真机浏览器上表现不佳再切换，`TranscriptionChannel` 缝不变。回退：继续批量方案。

### P1-B｜真模型高并发压测 + 限流桶按真实流量标定

> **状态：已完成，待用户验收**（2026-09-15）。证据：`P1-B-EVIDENCE.md`；报告 `docs/perf/M6-capacity.md` §2.7。
> 24 并发真流（V2 的 6 倍）0 供应商 429/5xx；标定 `ai_call 6→2`、`answer 8→2`（红-绿钉住 + 实证）；真调用 174/200。

- **现状**：`scripts/load_test.py` 已支持 `--scenario chat-sse --concurrency N --duration D`
  （不带 `--fake-llm` 即打真供应商）；V2 只压到 c≤4（避免打供应商）；限流是进程内
  token bucket（`ai_resilience/ratelimit.py`，rate/burst 来自 settings，burst=2.0）。
- **做什么**：真模型分级加压 c=8/16/32、**短时长**（每级 ≤30s），记录有效吞吐、我们
  429 拒绝路径 vs 供应商 429 的真实表现、错误率、p50/p95 首帧；据此**标定**
  `RateLimitSettings` 的 rate/burst（先红-绿补测试再改参数），输出 `docs/perf/`
  新容量报告（真模型节，不与假上游混表）。
- **交付物**：可复跑压测命令 + 原始输出 + 标定前后参数对照 + 测试用例。
- **验收口径**：数字入报告；限流参数变更有红-绿测试且写明标定依据；总量封顶
  （见 Q3），超出即停。
- **预估**：1 会话；真调用 ~60–120 次。
- **风险**：供应商抖动污染读数（多轮取中位数/注明时间窗）；真 429 可能触发重试放大——
  压测前确认重试上限行为。

## 4. 阶段级验收口径

- 每张票 = 一个可复跑脚本（或新参数）+ 验收文档一节 + 必要的 `PROBLEMS.md` 条目。
- 实时证据必须含：增量帧时间戳序列（首字延迟、帧间隔）、WS 端到端关闭码 1000、
  archive 事件样本；**不得**用批量结果冒充增量。
- 容量证据必须含：真实 `usage`/model 字段、端到端耗时分布、我们 429 与供应商 429
  分开计数；标定参数变更先红-绿。
- 真机证据（C）必须含：脱敏原始片段 + 字段映射表 + 失败原因；失败也留原始报错。
- 演练证据（D）必须含：故障注入窗口、恢复时间口径（不被探针超时截断，教训 P21 周边）、
  资源曲线。
- 未验证就写未验证；全部结论汇总到 `ACCEPTANCE.md`（含偏差）。

- 不做浏览器矩阵（Safari/Firefox/蓝牙耳机）——继续列入未验证，除非你点名要做。
