# P7 验收包：限流状态迁到 Redis（多副本共享一份配额）+ 显式降级语义

## 0. 一句话

限流桶的状态从「每副本一份」改成「Redis 上一份，N 个副本共享」，且**只共享供应商成本桶**
（`ai_call / answer / heavy`）；Redis 不可用时**降级到进程内桶**（配额退回本副本 = 迁移前的语义），
并把降级做成一等公民的可观测事实：`rate_limit_degraded` 计数 + `X-RateLimit-Scope: shared|instance`
响应头 + 30s 冷却窗口 + 50ms 单次超时（**不 fail-closed、不按快照拒绝**）。

### 2.4 D19 降级实验：`uv run python -m scripts.fault_probe fault --scenario redis-partition --seconds 20`

```
== shared bucket before the cut: scope=shared (waited 0.0s)
== cutting the api<->redis path for 20.0s (network disconnect)
== network path restored, waiting for the first success
fault window: {"timeout": 9}
recovery: 2327 ms after the fault ended
total=9 ok_during_fault=0
note: ratelimit_during_partition=401/instance
note: auth_during_partition=ReadTimeout
note: healthz_ok_during_partition=9
note: ratelimit_after_recovery=shared waited=10.1s
PASS: shared -> instance（降级、无 5xx）-> shared

```

读法与一条**提案没预见的事实**：Redis 分区期间，**认证路径自己也依赖 Redis**（`auth_during_partition=ReadTimeout`），
带 cookie 的请求根本走不到限流器。所以降级要在**认证之前**观测：用匿名请求（IP 身份，不碰会话存储）——
它拿到 401（业务语义，< 500）且 `scope=instance`，即"限流器降级了、没有把请求变成 5xx"。
恢复后 `waited=10.1s` 是冷却窗口（30s）里已经过去的部分 + 下一次重试成功，不是"Redis 一回来就立刻切回"。

## 4. 与提案的偏差（需要你认可）

1. **探针不钉 rate**。提案说给探针一个确定边界；实现时先按"把 ANSWER 桶钉成 capacity=1"做，
   结果**把 kill 演练自己的答题打成 429**（演练 exit=1，见 `PROBLEMS.md` P42）。改成
   "全新身份打 7 次 + 放行数 ≤ capacity+1 + scope=shared + Redis 有键"——探针与演练解耦。
2. **Q5（nightly 加降级实验）没有新增 workflow 步骤**：断言加进了 nightly 已经在跑的
   `redis-partition` 场景（`scripts/fault_injection_drill.sh:174` 调用）与 deploy 层的 compose_smoke。
   活动部件更少，但与提案字面（"nightly 增加实验"）不同，需你点头。
3. **compose_smoke 的配额断言是单侧边界**（≤ capacity+1）而不是严格等式：严格等式由
   `test_ratelimit_redis.py::test_two_replicas_share_one_quota`（rate=0.0001，无回填）保证；
   演练里容忍突发期间的自然回填。
4. 额外引入 `docs/perf/M6-capacity.md` §2.7 的"迁移后口径"行（提案说同步更新，落实为新增一行）。

## 5. 未验证项（诚实清单）

- **跨副本 wall-clock skew**：本机 compose 同宿主，测不出 skew；只写了影响上界（2/s 下每 100ms ≈ 0.2 token）。
- **多宿主生产形态**未验：单机 compose 上的共享配额 ≠ 跨主机时钟/网络条件下的行为。
- **Redis 键基数**只靠 TTL 兜底，未做每身份键数上限（提案 §5 已声明不做）。
- **配额收紧的真实影响**未实测：真机调用 0 次；"单身份 AI_CALL 从 4/s(burst 8) 收紧到 2/s(burst 4)"
  只在本机单测/演练口径下确认，未打真模型。
- **降级期间的延迟分布**未量化：只知道最坏是每请求一次 `socket_timeout`（50ms）、且在冷却窗口内为 0。
- **nightly 自然排程**要等下一跑（且需先合并进默认分支）：本票改的是 nightly 已经在跑的两个脚本，不是新增步骤。
- **kill 演练跑在热卷上**（compose_smoke 之后未 `down -v`）；冷卷证据来自 §2.2 那一轮。
