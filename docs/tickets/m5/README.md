## 1. M5 验收（§12.4 原文）

## 2. 范围边界

**做**：场景（Scene）与绑定（Binding）注册表 + 解析器（Resolver）；星云工作流 adapter
（HTTP + SSE 归一、Bearer apiKey:apiSecret、flow_id/uid/stream/chat_id/history/parameters、
Pydantic 强校验、错误三态、注入防御）；**显式输入/输出映射表**（拒绝旧项目的别名硬编码）；
双 adapter 契约测试套件（同一套用例跑两个实现 + 本地假星云服务端）；四条链路改为按场景解析
（服务层零改动）；场景设置端点与前端面板；双供应商端到端对照证据。

**不做**：把编排搬进星云（D04 明确自研编排是主线，星云只作第二 adapter）；神态/摄像头场景（D09 砍）；
星云文件上传（我们的简历解析是本地确定性解析，不需要云端 uploadFile）；按用户/按会话的绑定粒度（见 Q3）；
分布式配置刷新（M6）；星云工作流的可视化编辑。

**纪律**：红-绿 TDD；只 mock 系统边界（星云 HTTP/SSE、时钟、Redis）；内部模块不 mock；
**不做别名回退猜测**（旧项目坏味道#5 的反面教材，见 §9.1）；小步提交说 WHAT；问题即时记入 PROBLEMS.md。

## 4. 与原方案的取舍（对齐 D 决议 + M1–M4 经验）

1. **星云是"第二 adapter"，不是新主线**：D04 的顺序不变（自研编排 + OpenAI 兼容直连为主），
   星云 adapter 存在的意义是**证明接缝是真的**——同一场景换供应商，业务代码一行不改。
2. **拒绝别名硬编码（旧项目坏味道#5）**：星云工作流输出字段名不可控（旧项目硬编码
   `sugest/suggestions`、`score/total_score` 之类的回退链）。我们只做**显式映射表 + Pydantic 强校验**：
   字段对不上就报 `LlmSchemaError`（可重试一次 → 仍失败则失败），绝不猜。
3. **场景绑定的落点**：场景枚举 + DB 表（`llm_scene_bindings`）+ 进程内缓存 + 端点；
   迁移期默认全部绑定 openai_compat，**合并后行为与 M4 完全一致**（回归全绿是硬门槛）。
4. **解析发生在 HTTP 层，服务层零改动**：现有服务（chat / question / evaluation / follow-up / report）
   已经接收 `gateway: LlmGateway` 参数——这正是 M1 留下的接缝。M5 只把"怎么拿到 gateway"从
   "按 model_ref 查注册表"改成"按场景解析绑定"，**服务层文件不应出现在 diff 里**（T6 的验收方式）。
5. **韧性链继续在最外层**：星云调用同样走 M3 的 `run(stage, key, fn)`（stage 不变，key 不变），
   所以单飞/熔断/舱壁/超时/回放对两个 adapter 一视同仁——这是 M3 投资在 M5 的第二次兑现。
6. **诚实原则**：星云真机同样需要凭据（apiKey/apiSecret/flowId），T10 单列；
   CI 用**本地假星云服务端**（按 §4.1.8 的形状实现）跑契约测试，验收文档区分"契约级"与"真机"。

## 5. 环境事实（影响验收口径）

- 本机**没有星云凭据**（apiKey/apiSecret/flowId）→ 真机路径不可验证，同 M4 的处理方式（T10 待凭据）。
- 星云工作流是**云端黑盒编排**：我们只能控制"传什么、怎么解析回来"，无法在本地跑它的提示词；
  因此双 adapter 对照的公平口径是"同一场景、同一输入、同一输出 schema"。
- 现有四条链路都是**非流式**的结构化输出（出题/评分/追问/报告）＋一条流式（聊天）；
  星云 adapter 必须两者都支持，否则接缝不完整。
