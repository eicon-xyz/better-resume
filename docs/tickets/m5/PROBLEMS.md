## P0 — 工作流输出的别名诱惑（旧项目坏味道#5）

- **症状（来自架构分析 §9.1）**：旧项目对星云输出字段做了多别名回退（如 `sugest`/`suggestions`、
  `score`/`total_score`），契约实际上是靠猜。
- **风险**：M5 一旦也写回退链，就会把"云端字段名变了"这种事故变成静默的错误值（继续往下跑）。
- **对策**：T4 只做显式映射 + Pydantic 必需字段强校验，缺失即 `LlmSchemaError`；
  T4 专门有反例用例（旧别名必须不被接受）；T5 的契约套件对两个实现一视同仁。
- **证据**：待 T4/T5。

## P1 — 星云真机不可验证（环境事实）

- **症状**：本机没有 `apiKey/apiSecret/flowId`，无法验证真实 SSE 形状与输出字段。
- **修法**：契约测试用本地假星云服务端（形状按 §4.1.8 实现）；T10 单列真机票；
  验收文档明确写"真机未验证"。
- **证据**：待 T10。


## P2 — hygiene 守卫第一次抓到我自己（docstring 里的反引号转义）

- **症状**：全量测试里 tests/test_source_hygiene.py 红：scene_mapping.py 报 invalid escape sequence。
- **根因**：写 docstring 里的 Markdown 行内代码时把反引号转义了；非 raw 字符串里这是非法转义，
  本地 .pyc 缓存会掩盖这个告警 —— 这正是 M4 加守卫测试的原因。
- **修法**：docstring 改为 raw 字符串并去掉多余转义。
- **意义**：M4 的投入在 M5 第一次就回本了；跨里程碑的守卫测试比「记得小心」可靠。
- **证据**：修复后全量测试全绿。

## P3 — 按「第 N 次出现」打补丁把 interview.py 改坏（差点埋雷）

- **症状**：给三个端点换成按场景解析时，我用 `str.replace(old, new, N)` + `index(old_q)` 的顺序假设，
  结果 `_resolve_gateway`（报告总结）的 try/except 被替换成了答题端点的代码，answers 端点反而没改，
  文件里留下 `payload.model_ref` 在错误作用域的半截代码（ruff 报 15 个错才暴露）。
- **根因**：三个端点的 try/except 长得一模一样，靠「出现次序」定位在重构中不成立；
  而且 `_resolve_gateway` 不在计数里（它的缩进不同），顺序假设从一开始就是错的。
- **修法**：改为「区域锚点」——每个替换串带上下面一行（`state = request.app.state` + 目标行）或函数名，
  先断言唯一性再替换；helper 用函数边界整段重写。
- **教训**：重复代码里不许用序号定位；每次结构性改动后立刻 `ruff check` + 全量跑，
  半截代码活不过两分钟。
- **证据**：修复后 5 例路由用例 + 全量 506 例全绿。

## P4 — follow-up 与 evaluation 是同一次答题请求（场景切分的边界）

- **症状**：M5 有五个场景，但一次 `POST /answers` 同时触发评分与追问两个 AI 调用，
  而 `AnswerService.submit(...)` 只接收一个 gateway。
- **选项**：(a) 追问复用评分 gateway（服务层零改动，但 FOLLOW_UP 绑定形同虚设）；
  (b) 给 `submit()` 加一个可选 `follow_up_gateway`（服务层改 3 行，五个场景都真实生效）。
- **选择**：(b)。理由：M5 的验收就是「场景绑定真的生效」，留一个假绑定的场景会污染证据；
  这个改动是「路由两个场景」，与「切换供应商不改业务码」不冲突（已记入 T9 的偏差清单）。
- **证据**：tests/test_scene_routing.py::test_scoring_follows_the_evaluation_binding
  断言同一次请求里 evaluation 与 follow_up 两个绑定都被解析。
