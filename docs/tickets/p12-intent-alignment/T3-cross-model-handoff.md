## 目标

`docs/agents/subagents.md` §1–§7 讲的是**同仓多成员 / 子代理**：先建任务再派活、写范围不重叠、
结构化产出先给契约、证据用脚本核对、双轴评审不合并、席位与 fork、等待与超时。

它缺两样东西：

1. **规划方与执行方不是同一个模型**时的交接格式——同一份 spec 会被不同模型不同地解读，而这种解读差异正是意图漂移的放大器；
2. **评审方该由谁担当**——§5 只说了「双轴分开跑、不合并结论」，没说评审方与执行方要不要同款。

本票在文件末尾追加一节，把这两样定下来。

## 新节必须包含的内容

### 1. 何时用

执行方与规划方不是同一个模型或同一个会话时——含子智能体、`subagent_fork`、以及把票据交给另一款模型执行。

### 2. 交接包五栏（缺一不可）

| 栏 | 要求 |
| --- | --- |
| 范围 | 要读哪些文件（给路径）；读不到就别猜，停下来问 |
| 唯一写入路径 | 只许写这一个文件或目录；两个执行方写同一路径必然互相覆盖（§2 的既有结论） |
| 验收口径 | **可复跑命令 + 预期读数**（数字或字符串）。不许写「跑通即可」「无报错」 |
| 红线 | 不许碰的对象（文件、节、依赖、既有格式） |
| **不接受的自由度** | 明确列出执行方**不许自行发挥**的点 |

### 3.「不接受的自由度」要给定义 + 至少 4 个例子

定义：spec 没写、但执行方**不许自己补**的地方。它与「红线」的区别是——红线是不许碰的**对象**，
不接受的自由度是不许做的**判断**。例子（新节里至少写这四个，可再加）：

- 不许重排或重编号既有章节；
- 不许顺手重构与本次无关的代码或文档；
- 不许新增依赖；
- 不许把实现偏差写成新的业务规则（`AGENTS.md` 硬规则 3）；
- 不许扩大写入路径；
- 不许修改 spec 或票据的既有内容（只允许在末尾追加自己那两段自述）。

### 4. 冲突处理（必须写）

spec 与现实冲突、或需要的信息不在交接包里 → **停下来报**，不许自行补规格。
对应 `AGENTS.md` 硬规则 3：未经用户确认的实现偏差，不得写成新的业务规则。

### 5. 评审双轴分派（本票的重点）

| 轴 | 谁跑 | 唯一任务 |
| --- | --- | --- |
| **Spec 轴** | **异家族同级**模型（例：执行方是 `opencode-go/deepseek-v4.1-flash` → 评审方用 `dashscope/qwen3.8-flash`） | 比对「票据里的意图复述 / spec 与票据要求 / 实际 diff」三者，找出**不一致** |
| **Standards 轴 + 意图一致性** | 规划方（掌握意图与仓库规范的那一方） | 对照 `CODING_STANDARDS.md` 与票据红线，找违规与越界 |

必须写进新节的三条：

- 评审方与执行方**不同款（不同家族）**。子代理可用路由全是 flash 级、没有更强的档，
  所以这一栏的价值来自**盲区不共享**，不是「用更强的模型审」——**不要写成后者**。
- 评审的产出是**两轴并列的发现清单**，不合并、不重排（§5 的既有结论）。
- 评审的任务是**找不一致**，不是评价设计好坏；任务越窄，弱模型越可靠。

### 6. 为什么要单列「不接受的自由度」（写一句话就够）

指望模型自己判断边界，不如把不许发挥的地方显式写出来——执行模型越弱，这一栏越值钱。
