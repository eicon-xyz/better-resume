# P12 问题台账

难题与坑，按发现顺序记；每条写「现象 → 根因 → 处置」。

## 1. 长期文档被写进阶段编号（硬规则 2 违规）

- **现象**：`docs/agents/issue-tracker.md` 的新节里出现「适用于 p12 及之后的阶段」与「`docs/tickets/p11-*`」。
- **根因**：规划方的 T2 票据有一节标题就叫「适用范围（**必须写进新节**）」，正文明确要求写「p12 及之后」——spec 直接指示了违规，执行方忠实照做。
  `AGENTS.md` 硬规则 2 明文：临时性的开发阶段划分一律不进任何文档。
- **处置**：异家族 Spec 轴评审发现；文档改为不依赖编号的表述（「本节生效之后新建的票据与验收包」），票据 §适用范围 同步订正为「不得带阶段编号」。
  教训：**硬规则要能被 spec 自查**——规划方写票据时没拿硬规则过一遍自己的要求。
  边界：阶段编号出现在**该阶段自己的票据目录内**（`docs/tickets/<stage>/`）是 tracker 既有约定，不算违规；违规的是把它带进跨阶段的长期文档。

## 2. 两份并行产出的文档口径互相矛盾

- **现象**：`issue-tracker.md` 新写的「出现声明之外的路径 = 越界，直接判红」按字面会把本阶段每张票据（含 T2 自己）判红——
  票据头部的「唯一写入路径」只写目标文件，而阶段 spec 要求在票据末尾追加两段自述。同时 `docs/agents/subagents.md` §8.3 已经写了这个例外。
- **根因**：并行派活 + 规划方 spec 有洞（T1/T3 票据的「唯一写入路径」未排除自述段）。
  **机械守门全部通过**（numstat 零删除、sha256 基线无越界、grep 计数达标）——因为这不是越界，是语义矛盾。
- **处置**：补例外并指回 `subagents.md` §8.3（不抄原文，避免两份原文漂移）。
  教训：**机械守门抓越界，异家族评审抓矛盾，两者不可互相替代**。

## 3. 执行方自述的理由是编的

- **现象**：T1 的「实现决定交代」称：用缩进普通行而不用子列表，「因为验收命令要求 §6 里以 `- ` 开头的行 ≤ 8；若用子列表，一条会占 4 行、计数直接超标」。
  实测 `printf '  - a\n  - b\n- c\n' | grep -c '^- '` → **1**：`^- ` 锚定行首，缩进行不计数。理由不成立。
- **根因**：真实约束是票据给的样例格式（顶格 bullet + 两空格缩进）；执行方为自己的决定补了一个听起来合理但**未经验证**的理由。
- **处置**：异家族 Spec 轴评审核出，修复轮更正为真实理由（产物格式本身合规，只改自述）。
  教训：**自述里的「为什么」也必须能被实测证伪**，否则这一栏只是装饰；这一栏一旦失真，用户就无法靠它判断还有没有别的误判。

## 4. 票据未进 git → 评审无法核验票据本身有没有被改

- **现象**：T3 的 Spec 轴评审明确报「无法判定：票据正文 1–106 行是否被实现方动过」——目录 untracked，`git diff` 无输出；`session_search` 两次 30s 超时取不到规划方原文。
- **根因**：`docs/tickets/<stage>/` 在提交前是 untracked，git 提供不了基线。
- **处置**：规划方建 `var/p12-baseline/after-first-round.sha256` 与 `final.sha256` 快照，修复轮起可机械核验越界。
  教训：**派活前先给票据建基线**（retro 候选：写进 `docs/agents/subagents.md` §8 的交接准备）。

## 5. 规划方的验收命令与并行票互斥

- **现象**：T2 票据 §验收 期望 `git status --porcelain … docs/agents/subagents.md` 无输出，但 README 明确允许 T3 修改该文件；两票并行时这一行必然不成立。
- **根因**：票据是按串行写的，派活是并行的。
- **处置**：授权执行方更正该行为「`subagents.md` 的改动只来自 T3」；记为规划方缺陷。

## 6. 规则成本检验把「能力指针」当成「冗余规则」

- **现象**：T4 把 `AGENTS.md` §贡献指南里「可选：启用仓库内 git hooks」列为删除候选，理由是它跑的两件事 CI 已覆盖。
- **根因**：票据没让执行方先区分 **规则 / 指针 / 事实记录**；成本对称性检验只适用于「要求你做 X」的规则，
  而这一条是「这里有个可选能力、怎么开启」的唯一发现入口，删掉是丢信息不是去冗余。
- **处置**：规划方否决该候选。教训：检验对象要先分类，再套判定表。

## 7. 规划方票据里的计数检查本身是脆弱的

- **现象**：T1 票据用 `awk '/^## 6/,0' | grep -c '^- '` 断言「必答问题 ≤ 8 条」，实际数的是**所有顶格 bullet**，不是问题条数。
- **根因**：规划方把「条数上限」直接翻译成一个 grep，没检查这个 grep 数的是什么。执行方被迫绕它，并为绕法编了理由（见 §3）。
- **处置**：本轮未改检查（产物合规、计数恰好为 8）；记为规划方缺陷。
  教训：**断言要先证明它数的是你想数的东西**——这与 D22「只打印结论、不判定的验证脚本视为缺陷」是同族问题。
